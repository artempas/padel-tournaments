# Падел Турниры

Веб-приложение для турниров по паделу в форматах **Американо** и **Мексикано**: вносим
игроков и число кортов, приложение само составляет расписание, организатор вносит счёт
после каждого матча, в конце показывается итоговая таблица.

- **Стек:** Next.js 15 (App Router) · TypeScript · PostgreSQL · Tailwind CSS v4
- **Авторизация:** passkey (WebAuthn) и Яндекс ID, без паролей
- **Дизайн:** mobile first

## Быстрый старт

```bash
npm install
cp .env.example .env.local
npm run db:up
npm run db:migrate
npm run dev
```

Откройте http://localhost:3000, зарегистрируйтесь по passkey — и создавайте турнир.

## Деплой

Инструкция для Synology NAS — [DEPLOY.md](DEPLOY.md). Коротко: один контейнер
плюс внешний PostgreSQL, схема применяется при старте. Обязательное условие —
HTTPS и домен, без них passkey не работает.

## Переменные окружения

| Переменная     | Назначение                                                        |
| -------------- | ----------------------------------------------------------------- |
| `DATABASE_URL` | Строка подключения к PostgreSQL                                    |
| `RP_ID`        | Домен для passkey — без схемы и порта (в разработке `localhost`)   |
| `RP_NAME`      | Название, которое видит пользователь в диалоге passkey             |
| `ORIGIN`       | Полный origin, который видит браузер; несколько — через запятую    |
| `YANDEX_CLIENT_ID`     | Идентификатор приложения Яндекс ID — необязательно         |
| `YANDEX_CLIENT_SECRET` | Секрет того же приложения; только на сервере               |
| `YANDEX_REDIRECT_URI`  | Только если Redirect URI не выводится из `ORIGIN`          |

`RP_ID` должен быть регистрируемым доменом сайта, а `ORIGIN` — точным адресом
с протоколом и портом. При деплое, например: `RP_ID=padel.example.com`,
`ORIGIN=https://padel.example.com`. WebAuthn работает только по HTTPS
(исключение — `localhost`).

Пары `YANDEX_*` нет — нет и кнопки «Войти с Яндекс ID»; всё остальное работает
как раньше. Как завести приложение — ниже, в разделе про авторизацию.

## Если пропали стили

`next dev` и `next build` пишут в одну и ту же папку `.next`. Если запустить сборку,
не остановив дев-сервер, тот начнёт отдавать 404 на `/_next/static/css/app/layout.css`,
и страница откроется вообще без оформления. Лечится так:

```bash
rm -rf .next && npm run dev
```

Правило простое: не запускайте `npm run build`, пока работает `npm run dev`.

## Как устроен турнир

### Расписание (Американо)

Цель формата — чтобы **каждый сыграл в паре с каждым ровно один раз**. Для этого нужно
`ceil(C(n,2) / 2)` матчей: например, 14 матчей на 8 игроков.

Генератор ([`src/lib/americano.ts`](src/lib/americano.ts)) соблюдает три правила:

1. в каждом матче четыре разных игрока, двое на двое;
2. игрок не может одновременно играть на двух кортах — в раунде он встречается один раз;
3. когда игроков не кратно четырём, кто-то отдыхает, и отдых распределяется поровну
   (разница в числе игр между любыми двумя игроками — не больше одной).

Работает в две фазы: сначала десятки быстрых рандомизированных сборок раунд за раундом,
затем полировка лучшей — обмены игроками местами по всему расписанию, если это
выравнивает пары. Повторная пара наказывается на три порядка сильнее, чем повторный
соперник, поэтому сначала закрываются все партнёрства и лишь потом разнообразятся
соперники.

Идеальное расписание существует математически только при `n ≡ 0 или 1 (mod 4)`. Для
остальных `n` число пар нечётно, и минимум одна пара обязана повториться — генератор
достигает этого минимума. Фактический результат для всех размеров от 4 до 32 игроков:
все пары покрыты, повторов не больше теоретического минимума, худшее время — 250 мс.

Число кортов ограничивает матчи в раунде: `min(корты, ⌊игроков / 4⌋)`. Лишние корты
просто не используются, о чём форма создания предупреждает заранее.

### Расписание (Мексикано)

Здесь пары не тасуются заранее, а следуют из таблицы: раунд — функция от текущих
результатов, поэтому раньше последнего счёта его не существует.

Генератор ([`src/lib/mexicano.ts`](src/lib/mexicano.ts)) собирает раунд так:

1. первый раунд разыгрывается жребием — таблицы ещё нет, и порядок ввода игроков не
   должен ничего решать;
2. дальше игроки берутся в порядке таблицы и режутся на четвёрки: первая четвёрка — на
   первый корт, вторая — на второй;
3. внутри четвёрки играют 1-й с 4-м против 2-го с 3-м;
4. когда игроков не кратно четырём, отдыхают те, у кого больше сыгранных матчей, а при
   равенстве — те, кто ниже в таблице. Так отдых продолжает ходить по кругу.

Формат сам по себе не кончается, поэтому длину в раундах задаёт организатор
(`tournaments.rounds_planned`, 1–30). Матчи следующего раунда пишутся в базу той же
транзакцией, что и последний счёт предыдущего (`extendMexicano` в
[`src/lib/tournaments.ts`](src/lib/tournaments.ts)).

Уже созданный раунд не пересобирается, даже если счёт поправят задним числом: люди к
этому моменту стоят на кортах, и менять составы под ними хуже, чем оставить раунд,
собранный по прежней таблице.

Отсюда же следствие для офлайна: счёт сохраняется на устройстве и уходит сам, но
следующий раунд появится только после того, как результаты дойдут до сервера.

### Счёт

Матч играется не по правилам падела, а до фиксированной суммы очков на двоих —
по умолчанию **16**. Сервер это и проверяет: счёт принимается, только если
`score1 + score2` равно значению турнира, так что 10:10 будет отклонено.

В интерфейсе очки одной пары автоматически дополняют очки другой, поэтому ошибиться
нельзя. Результат можно перевнести или сбросить.

### Игроки между турнирами

Каждое имя, введённое при создании турнира, попадает в постоянный список
клуба (`people`). Сравнение имён регистронезависимое, поэтому
«Артём» и «артём» — один человек, а исправление опечатки обновляет игрока,
а не плодит дубль. Нормализацию делает `normalizeKey()` из `src/lib/normalize.ts`,
результат лежит в `people.name_key` — база собственных правил сравнения не имеет,
поэтому разойтись с приложением не может.

Это даёт три вещи:

- на экране **Игроки** видно рейтинг, суммарный счёт по всем турнирам, число
  матчей, побед, разницу и среднее за матч;
- при создании турнира сохранённые игроки предлагаются чипами в один тап;
- у завершённого турнира есть кнопка **Новый турнир с этим составом** —
  она открывает форму с теми же людьми, кортами и очками за матч.

Удаление игрока из списка не трогает сыгранные турниры: строка в `people`
остаётся, ей лишь проставляется `archived_at`. Связь `tournament_players.person_id`
помечена `ON DELETE RESTRICT`, так что стереть человека с историей база просто
не даст. Пропадает только предложение при создании нового турнира. Игрока, за
которым закреплён аккаунт, спрятать нельзя вовсе — см. «Клубы».

Название турнира подставляется случайное («Пятничный американо», «Вечерний
слэм») — примерно в половине случаев оно намекает на день недели или время
суток. Кнопка 🎲 рядом с полем перебирает варианты.

### Досрочное завершение

Турнир можно остановить, не доиграв — кнопка **Завершить турнир досрочно** внизу
вкладки «Матчи». Несыгранные матчи просто остаются без счёта и не попадают в
таблицу; итоги считаются по тому, что успели сыграть. Из баннера турнир можно
вернуть в игру кнопкой **Продолжить турнир**.

Обычно статус вычисляется сам: «завершён», когда у всех матчей есть счёт. Ручное
закрытие поэтому пишется отдельным флагом `tournaments.closed_manually` — иначе
правка счёта в закрытом турнире пересчитала бы статус обратно в «идёт». По той же
причине `finished_at` при повторном сохранении счёта не сдвигается.

Метка «досрочно» показывается, только пока действительно есть несыгранные матчи:
если организатор закрыл турнир, а потом доиграл остаток, это обычное завершение.

### Итоговая таблица

Очки игрока — **сумма всех очков, набранных его парой во всех матчах**, где он
участвовал. При равенстве выше тот, у кого лучше разница забитых и пропущенных,
затем — у кого больше побед. Турнир автоматически помечается завершённым, когда
внесён счёт последнего матча.

### Рейтинг

Таблица турнира не знает, против кого набраны очки, — это знает рейтинг
([`src/lib/rating.ts`](src/lib/rating.ts)). Работает он как Elo, но результатом
матча служит не победа, а **доля набранных очков**: матч играется до
фиксированной суммы, поэтому счёт уже нормирован, и 12:4 — это ровно 0.75.
Схлопывать результат в «выиграл / проиграл», как в шахматах, здесь не нужно.

```
Ra = (r1 + r2) / 2                          сила пары — среднее двоих
expected = 1 / (1 + 10^((Rb − Ra) / 180))
actual   = очки стороны / сумма очков матча
Δ        = K × (actual − expected)          каждому в паре целиком
```

Отсюда главное свойство: **важен не результат, а разница с ожидаемым**. Пара с
перевесом в 86 пунктов обязана выигрывать примерно 12:4 — выиграв ровно
столько, она не получит ничего, выиграв 10:6, потеряет рейтинг, а разгром в 14:2
принесёт прибавку. Знаменателем служит сам счёт, а не норма турнира, поэтому
вечер до 16 очков сравним с вечером до 32.

Все начинают со **100**. `K` затухает с опытом — 18 до десяти матчей, 14 до
тридцати, дальше 11: новичок за один вечер находит своё место, ветеран не
скачет от одного неудачного турнира. Число матчей поэтому стоит в таблице рядом
с рейтингом: 104 после шести матчей и 104 после двух сотен — разные числа.

Три константы подобраны вместе, и порознь их менять бессмысленно. Величина шага
от стартового рейтинга не зависит вообще; расстояние, на которое игроки в итоге
расходятся, задаёт делитель: равновесие наступает на разрыве
`180 × log10(доля / (1 − доля))`. При 180 клуб за сезон расселяется примерно по
40…160 — крайние отличаются вчетверо. Ниже нуля при этом не уходит никто: на
прогоне в 700 матчей с нарочно перекошенным составом худший остановился на 37.

### Ступени

Число — для тех, кто в него вглядывается; для взгляда мельком есть ступень:

| Ступень | С рейтинга |
| --- | --- |
| 💎 Алмаз | 150 |
| 🔷 Платина | 130 |
| 🥇 Золото | 110 |
| 🥈 Серебро | 80 |
| 🥉 Бронза | ниже 80 |

Серебро шире соседей намеренно: это ступень «как все», на ней стоит старт и
толчётся середина клуба. Будь она такой же узкой, средний игрок прыгал бы между
серебром и золотом от одного удачного вечера.

Первые 10 матчей ступени нет — вместо неё вопросительный знак. Рейтинг новичка
за вечер гуляет на пол-шкалы, и вешать на него бронзу значило бы соврать.
Граница та же, что у самого большого `K`: ровно столько длится ускоренная
сходимость. Само число при этом видно сразу.

Ступень считается от **округлённого** рейтинга, а не от внутреннего дробного:
иначе 109.6 показалось бы как «110» с серебряным значком, ровно на пороге
золота.

Значки — SVG-спрайт в [`src/components/TierIcon.tsx`](src/components/TierIcon.tsx),
а не файлы в `public`: приложение работает без сети, и всё, что грузится
отдельным запросом, пришлось бы отдельно класть в кэш service worker. Спрайт
объявляется один раз на экран, строки таблицы ссылаются на него через `<use>`.

Рейтинг **не хранится**. Он функция от истории и считается по ней целиком при
каждом чтении — как и статус турнира. Правка счёта задним числом пересчитывает
всё сама, рассинхронизироваться нечему, а таблицы, которая могла бы разойтись с
матчами, просто нет. Порядок матчей при этом решает (Elo путезависим) и задаётся
парой «когда создан турнир, какое место матча в сетке», а не `played_at`: эта
метка сдвигается при перевнесении счёта, и тогда исправление опечатки в давнем
матче переписывало бы всю историю рейтинга.

В таблице турнира рядом с именем стоит, сколько этот турнир игроку принёс.
Считает это уже клиент: сервер присылает рейтинг участников на начало турнира
(`ratingBefore`), а матчи у клиента свои — поэтому дельта пересчитывается прямо
при вводе счёта и одинаково работает с очередью неотправленных результатов.

Рейтинг живёт внутри ростера одного организатора и глобальным не является:
сравнивать числа двух клубов, которые друг с другом не играют, бессмысленно.

### Картинка с результатами

Кнопка **Поделиться картинкой** на вкладке «Таблица» собирает PNG с названием
турнира, победителем и всей таблицей — то, что отправляют в чат сразу после
последнего матча.

Картинка рисуется на canvas прямо в браузере
([`src/lib/results-card.ts`](src/lib/results-card.ts)): ни запроса к серверу, ни
сторонней библиотеки, поэтому она собирается и без сети — как и всё остальное на
корте. Цвета тёмной темы зашиты в модуль: картинка уходит в чужой чат, где нет ни
наших CSS-переменных, ни выбранной пользователем темы.

Собирается она при открытии шторки, а не по нажатию кнопки: системный диалог
отправки открывается только по живому нажатию, а ожидание canvas между нажатием и
вызовом `navigator.share` это нажатие обесценивает. Заодно видно, чем именно
делишься. Где отправка файлов не поддерживается — обычно на десктопе — остаётся
кнопка «Скачать картинку».

Заголовок и подпись под ним считает `resultsSummary`: тем же текстом
подписывается сама отправка, чтобы получателю без картинки была видна суть.

## Авторизация

Два способа войти — passkey и Яндекс ID. Паролей в системе нет вообще.

- Регистрация и вход используют WebAuthn через `@simplewebauthn`.
- Вход можно начать **без имени**: браузер сам предложит подходящий passkey
  (discoverable credential).
- Challenge хранится в базе, а в cookie кладётся только его непредсказуемый
  идентификатор. Клиент не может подсунуть свой challenge, поэтому перехваченный
  ответ аутентификатора нельзя переиспользовать. Challenge одноразовый.
- В cookie сессии лежит случайный токен, в базе — только его SHA-256. Утечка дампа
  базы не даёт валидную сессию.
- Один аккаунт может иметь несколько passkey — например, телефон и ноутбук.

Аккаунт нужен только тому, кто заходит в приложение. Игроки в ростере — просто
имена, пока кто-нибудь из них не назовётся собой, приняв приглашение в клуб.

### Яндекс ID

Кнопка «Войти с Яндекс ID» появляется, когда заданы `YANDEX_CLIENT_ID` и
`YANDEX_CLIENT_SECRET`. Оба способа входа равноправны: аккаунт может иметь и
passkey, и Яндекс, и что-то одно.

Как это устроено:

- Authorization Code Flow с PKCE. Токен Яндекса не покидает сервер и нигде не
  сохраняется: профиль читается один раз в обработчике коллбэка, а наружу
  уходит обычная сессия приложения — та же, что и после passkey.
- `state` и PKCE-верификатор живут в httpOnly-cookie `padel_oauth` ровно десять
  минут — столько же, сколько код подтверждения у Яндекса. Кука одноразовая:
  коллбэк снимает её при любом исходе.
- Аккаунты связывает `id` пользователя Яндекса, а не логин: логин меняют, id
  закреплён навсегда. Лежит это в таблице `oauth_accounts`.
- Слияния с существующим аккаунтом по почте нет — почты приложение и не видит.
  Да и верить чужому адресу как доказательству «это тот же человек» значило бы
  отдать аккаунт всякому, кто заведёт такой же ящик. Связать входы можно только
  изнутри — в разделе «Аккаунт» своего профиля.
- Прав у Яндекса не запрашивается никаких: `scope` в запрос не уходит вовсе.
  `id` и логин Яндекс отдаёт всякому токену, а больше приложению и не нужно —
  ни имени, ни почты, ни портрета. Что именно разрешено, задано в кабинете
  приложения; код на это не влияет и лишнего попросить не может.
- Первый вход через Яндекс — это регистрация, и имя человек выбирает сам на
  экране «Как вас зовут?»: логин Яндекса стоит там подсказкой, но остаётся
  логином, а не приговором для турнирной таблицы. Только после этого появляются
  аккаунт и личный клуб — ровно как при регистрации по passkey.
- Пока имя не выбрано, аккаунта не существует: начатая регистрация живёт
  пятнадцать минут в `oauth_signups`, а в cookie лежит только её
  непредсказуемый id. В базе, а не в cookie, по той же причине, что и
  WebAuthn-challenge, — в ней записано, кто именно подтвердил себя у Яндекса,
  то есть готовый пропуск в аккаунт, а подписать cookie приложению нечем.
  Брошенная на полпути регистрация не оставляет ничего.
- Занятое имя — честная ошибка, а не повод придумать замену с номером: форма
  остаётся на экране, и начатая регистрация на неудачную попытку не тратится.
- Отвязать Яндекс можно, только если у аккаунта есть passkey: иначе входить
  будет нечем.

Регистрация приложения (делается руками на https://oauth.yandex.ru):

1. Создать приложение — **«Для авторизации пользователей»**.
2. Платформа **Веб-сервисы**, Redirect URI — адрес коллбэка, точно совпадающий
   по схеме, хосту, порту и пути:
   `https://padel.example.com/api/auth/yandex/callback`.
3. Права можно не выдавать никаких: приложению хватает `id` и логина, которые
   Яндекс отдаёт и так. Если мастер регистрации требует отметить хоть что-то,
   выберите самое безобидное — на вход это не влияет.
4. Для разработки завести **отдельное** приложение с
   `http://localhost:3000/api/auth/yandex/callback`: смешивать тестовые и
   боевые Redirect URI в одном приложении Яндекс не советует.

Стоит пройти [верификацию сервиса](https://yandex.ru/dev/id/doc/ru/confirm-account):
без неё на экране согласия висит предупреждение, и до конца входа доходят не
все.

## Клубы

Данные разложены не по аккаунтам, а по клубам: ростер, турниры и рейтинг
принадлежат клубу. Аккаунт даёт вход, клуб — то, что видно после него. Состоять
можно в скольких угодно клубах, и в каждом у человека своя роль и свой игрок.
При регистрации клуб заводится сам, и его владелец — новый аккаунт: состояния
«клуба нет» в приложении не бывает.

Текущий клуб выбирается селектором в шапке и живёт в httpOnly-cookie
`padel_club`. В адресах его нет: турнир адресуется своим id, а можно ли его
открыть, выводится из членства в `tournament.club_id` — поэтому ссылка на турнир
работает из любого клуба, где человек состоит. Cookie — подсказка, а не право:
каждое чтение сверяется с `club_members`.

### Роли

| | участник | администратор | владелец |
|---|:---:|:---:|:---:|
| смотреть турниры клуба | ✓ | ✓ | ✓ |
| вносить счёт в своих матчах, пока турнир идёт | ✓ | ✓ | ✓ |
| править любой счёт, в том числе в завершённом | | ✓ | ✓ |
| создавать турниры, завершать досрочно, продлевать | | ✓ | ✓ |
| убирать игроков из ростера | | ✓ | ✓ |
| звать людей ссылкой, менять роли | | ✓ | ✓ |
| удалять участников и турниры, передавать клуб | | | ✓ |

Роль повышают не выше своей и не трогают равного: администратор не понижает
другого администратора и не назначает владельца. Владельцем становятся только
через передачу клуба — отдельное действие, после которого прежний владелец
остаётся администратором.

Единственное, чего не может владелец, — выйти из клуба: сначала передать.

Все правила записаны один раз, в `src/lib/permissions.ts`. Модуль чистый, и
сервер с клиентом зовут одни и те же функции; скрытая кнопка — вежливость, а
проверяет права всё равно роут.

### Участник клуба — это всегда игрок клуба

По умолчанию игроки анонимны: имя в ростере и ничего больше. Приняв
приглашение, человек называет себя — выбирает существующего игрока (и получает
всю его историю) или заводит нового. Обратной ситуации не бывает: участника без
игрока запрещает отложенный триггер `club_members_have_player`, поэтому у «моего
профиля» нет пустого состояния.

Выход из клуба снимает и членство, и связь: игрок остаётся в ростере со всеми
матчами, снова анонимный. Удаление участника владельцем делает ровно то же.
Поэтому игрока, за которым стоит аккаунт, нельзя заархивировать — иначе получился
бы участник клуба, которого в клубе не видно.

### Ссылки-приглашения

У клуба одна действующая ссылка, живёт семь дней, пускает сколько угодно людей и
всегда участником. Выпуск новой гасит прежнюю. Токен хранится в базе открытым
текстом, а не хешем, как у сессий: ссылка должна быть видна на странице клуба
с любого устройства и после перезагрузки, а не только там, где её выпустили.
Цена этого решения мала — приглашение даёт роль обычного участника и ничего
больше.

QR-код рисует сторонний сервис [quickchart.io](https://quickchart.io/qr) —
собственного рендера в приложении нет. Значение ссылки уходит к нему открытым
текстом параметром запроса; приемлемо по той же причине, по которой токен и так
не засекречен. Логотип по центру (`centerImageUrl`) добавляется, только если
адрес приложения виден снаружи: сервис сам ходит за картинкой своим сервером и
localhost или частную сеть разработки не достанет — тогда просто рисуется код
без логотипа, а не битая картинка.

## Приложение на телефон и работа без сети

На корте связь обычно хуже, чем игроки, поэтому приложение ставится на домашний
экран и не требует интернета, чтобы вести счёт.

**Установка.** Есть манифест (`src/app/manifest.ts`) и иконки, так что Android
предлагает «Установить приложение», а на iOS работает «Поделиться → На экран
Домой». Открывается без адресной строки, стартовая страница — список турниров.

**Счёт без сети.** Сохранение больше не ждёт сервера: результат сначала
попадает в очередь в IndexedDB (`src/lib/offline.ts`), и только потом уходит
запросом. Поэтому шторка со счётом закрывается мгновенно, а вылет связи,
заблокированный экран или закрытая вкладка ничего не теряют.

- Очередь ключуется по матчу: повторный ввод счёта заменяет неотправленный,
  а не шлёт оба.
- Экран турнира рисуется как «последнее состояние сервера + очередь сверху»
  ([`src/lib/pending-scores.ts`](src/lib/pending-scores.ts)), включая пересчёт
  статуса, — итоговая таблица открывается на последнем матче и без сети.
- Неотправленные матчи помечены, сверху — сколько результатов ждёт отправки.
  Очередь уходит сама по событию `online`, есть и кнопка «Отправить сейчас».
- Отказ сервера (400 — например, сумма очков не сходится) снимает результат с
  очереди и показывает ошибку: иначе он навсегда заблокировал бы всё, что за
  ним. Обрыв связи, 401 и 5xx — наоборот, оставляют счёт в очереди.

Досрочное завершение и удаление турнира в очередь не попадают — это редкие
действия, они требуют связи. Но экран их всё равно не ждёт: см. следующий
раздел.

**Кэш страниц.** Service worker (`public/sw.js`) ходит в сеть первым и держит
копию на случай отказа: турнир, который открывали раньше, откроется и в подвале.
Для незнакомой страницы показывается `public/offline.html` — намеренно обычный
файл, а не роут Next: React-странице нужны свои чанки, а их в этот момент как раз
и не скачать. `/api/*` не кэшируется никогда, а при выходе из аккаунта кэш
страниц и очередь стираются.

Регистрируется worker только в продакшене: `next dev` пересобирает чанки на
каждое изменение, и кэш отдавал бы 404 — ровно та беда, что описана выше про
пропавшие стили.

## Optimistic UI

Клиент живёт по одному правилу: **экран показывает результат действия сразу,
запрос уходит следом, а отказ откатывает изменение и объясняется словами.**
Спиннеров и заблокированных кнопок в ожидании сети нет — на корте телефон в
одной руке, ракетка в другой, и ждать ответа, чтобы увидеть собственный клик,
там некогда.

Механика — в [`src/lib/optimistic.ts`](src/lib/optimistic.ts): изменение
описывается четырьмя вещами — что показать (`next`), как это отменить (`undo`),
какой запрос за этим стоит (`send`) и что сказать при отказе (`message`).
Два решения там стоит объяснить:

- `undo` — функция от текущего состояния, а не снимок на момент клика. Пока
  запрос шёл, на экране могли появиться другие правки, и они не должны пропасть
  вместе с откатом.
- Сами запросы выстроены в очередь: два изменения одного ресурса, ушедшие
  разом, иначе перезаписали бы друг друга ответами. Экрана это не касается — он
  всё показал ещё до очереди.

Это не `useOptimistic` из React: тот держит правку до конца transition и
возвращается к базовому значению, а базовое здесь приходит из props ровно один
раз — после `router.refresh()` компонент остаётся со своим состоянием.

Что этому правилу подчиняется:

| Действие | Что видно сразу | Если сервер откажет |
| --- | --- | --- |
| Счёт матча | шторка закрывается, счёт и таблица пересчитаны | результат остаётся в очереди (см. выше) |
| Завершить досрочно / продолжить | статус и вкладка «Таблица» | статус возвращается, сверху причина |
| Удалить игрока | строка пропадает из списка | игрок возвращается, сверху причина |
| Удалить турнир | переход в список турниров | возврат на турнир вместе с причиной |

Три исключения, и все три намеренные: **создание турнира** ждёт ответа, потому
что id и расписание рождаются на сервере — показывать до ответа просто нечего;
**вход** ждёт аутентификатор; **выход** ждёт сервер, потому что показать выход,
не погасив сессию, — соврать про безопасность.

Текст ошибки берётся от сервера, а обрыв связи отличается от отказа: `fetch`
бросает `TypeError` ровно тогда, когда до сервера не достучались, и тогда
виновата связь, а не введённое ([`src/lib/request.ts`](src/lib/request.ts)).

## Схема данных

Модели описаны в `prisma/schema.prisma`, но Prisma не умеет выражать
CHECK-ограничения, триггеры и вью — они написаны руками в SQL миграции.
Граница проведена так: индексами и внешними ключами владеет Prisma (иначе
`migrate dev` посчитает их дрейфом и снесёт), а всем, чего в её языке нет, —
миграции. Пересечения нет, значит нет и конфликта.

Что проверяет сама база, а не код: участники матча принадлежат его турниру;
игрок не занят на двух кортах в одном раунде; в матче ровно четверо; сумма
очков равна норме матча; человека с историей нельзя удалить; в клубе ровно один
владелец; участник клуба связан с игроком этого клуба, и наоборот.

Три последних — про количество строк в соседней таблице, ограничением такое не
выразить. Их держат отложенные до COMMIT триггеры, и отложены они не для
красоты: вступление в клуб пишет игрока и членство двумя запросами, а передача
владения на миг оставляет в клубе двух владельцев.

Статус турнира не хранится — он выводится из `completed_at` и `closed_at`
во вью `tournament_overview`. Итоговая таблица и сводка по людям — тоже вью
(`tournament_standings`, `person_career`) над общей `match_results`.

`rounds_planned` осмысленно ровно для одного формата, и за этим следит база:
CHECK `tournaments_rounds_planned_format` требует, чтобы длина была задана у
`mexicano` и не задана у остальных.

## Что дальше

Из трёх значений `tournament_format` генератора нет только у
`team_americano` — турниры фиксированными парами. Раскладка участников по
строкам `match_participants` этого не ограничивает: в паделе на корте всегда
четверо, меняется только способ разбивки на пары.
